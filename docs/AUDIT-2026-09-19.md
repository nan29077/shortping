# 전체 기능 점검 보고서

2026-09-19 · 대상 커밋 `c7a9ae4` + 이번 점검 수정분 · 점검 환경: Linux 검증 샌드박스(Node 22, SQLite), Chromium

## 점검 방법

1. **코드 정적 검토** — 서버 3파일(인증·결제·스튜디오/관리자 API), 정산·세무 엔진, 프런트엔드 16파일을 3개 축(권한·금액·화면)으로 나눠 전수 읽기.
2. **런타임 점검** — 실제 서버를 띄워 역할별 접근 통제 매트릭스, 잘못된 입력 12종, 결제 3종 전 과정, 출금·세금 계산, 월 마감 멱등성까지 60여 개 항목을 API로 직접 호출해 검증(`실패 0건`).
3. **화면 점검** — 시청자 12화면 + PD 9화면 + 관리자 16화면, 총 37화면을 브라우저로 열어 콘솔 오류·5xx 응답·빈 화면·무한 스피너·가로 넘침 확인(`문제 0건`).
4. **회귀 테스트** — 통합 테스트 38개, TypeScript, 프로덕션 빌드 전부 통과.

## 확인 결과 문제 없던 부분

- **권한 경계**: 시청자·PD·관리자·비로그인 4종 × 주요 엔드포인트 전수 호출에서 권한 이탈 0건. 타 PD의 작품·파일·정산·출금에 접근 불가, 미소유 자원은 404로 통일(존재 여부 노출 방지).
- **결제 정합성**: 금액은 항상 서버의 작품 정보·설정값으로 계산(클라이언트 금액 무시), `idempotency_key` UNIQUE + 사용자 행 잠금으로 중복 결제 차단, 회차 구매는 산 회차만 열리고 다음 회차는 계속 잠김, 시청 기록 저장도 같은 권한 검사를 통과해야 기록됨.
- **정산 산식**: 모든 정산건에서 `판매액 = 플랫폼 수수료 + 결제 수수료 + 정산액` 성립 확인. 주문 합계와 정산 원장 판매액 합계 일치.
- **출금 상태 머신**: 신청 → 승인 → 지급 완료, 반려 시 정산건 복구, 지급 완료 건 재처리 409, 반려 사유 필수.
- **월 마감**: 진행 중인 달 마감 차단, 같은 달 두 번 마감해도 중복 정산 없음(결정적 ID + 늘어난 회차만 계산).
- **업로드·심사**: 파일 헤더 검증 + FFmpeg 첫 프레임 디코딩, 본인 업로드 파일만 연결, 심사 통과 전 비공개, 1화부터 연속 회차 검사.
- **보안 기본기**: scrypt + 상수 시간 비교, 세션 토큰은 해시만 저장, HttpOnly·SameSite 쿠키, Origin 검사, 전 구간 파라미터 바인딩(SQL 인젝션 없음), 오류 메시지에 내부 정보 노출 없음.
- **화면**: 37개 화면 전부 정상 렌더링, 콘솔 오류·5xx·무한 스피너·가로 넘침 0건.

## 남은 권고 (이번 범위 밖)

1. **시청량 기반 정산 고도화** — 현재 배분 가중치는 "새로 도달한 회차 수"입니다. 실제 시청 시간(progress)이나 회차별 시청 이벤트 로그를 쌓으면 더 정확해집니다. 클라이언트가 회차 번호만 보내도 가중치가 오르는 구조라 정산 규모가 커지기 전에 이벤트 검증이 필요합니다.
2. **설정 캐시 전파** — 운영 설정은 프로세스 메모리에 캐시됩니다. 인스턴스를 여러 개로 늘리면 요율 변경이 다른 인스턴스에 즉시 반영되지 않습니다(짧은 TTL이나 알림 채널 필요).
3. **`TRUST_PROXY_HOPS` 미설정 경고** — 프록시 뒤에서 이 값을 빠뜨리면 요청 제한이 전체 사용자 공용 버킷이 됩니다. 운영 모드 부팅 시 경고나 차단 권장.
4. **Origin 헤더 없는 변경 요청** — 현재는 통과시킵니다. SameSite=Lax 쿠키가 1차 방어선이라 실제 위험은 낮지만, 필요하면 Referer 폴백 검증 추가.
5. **관리자 회원 API 이중화** — `/api/admin/users/:id`와 `/api/admin/members/:id`가 공존합니다(전자는 세션 정리 없음). 하나로 통합 권장.
6. **월 마감 순서** — 늘어난 회차만 계산하는 구조라 월을 건너뛰거나 역순으로 마감하면 이전 달 몫이 집계되지 않습니다. 순서대로 마감하는 운영 규칙이 필요합니다.
