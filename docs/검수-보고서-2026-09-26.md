## 3. 우선 수정해야 할 결함

P1은 권한·비용·심사·배포에 영향을 주므로 해당 기능의 외부 공개 전에 수정할 항목입니다. P2는 특정 사용자 동작에서 잘못된 결과나 불편을 일으키므로 다음 안정화 작업에 포함할 항목입니다.

### P1-01. 협업 프로젝트 밖의 비공개 미디어 접근 허용

- 위치: [collab.mjs](../server/ai/collab.mjs)의 `sharesWith()` 82~88행, [routes-studio-ai.mjs](../server/ai/routes-studio-ai.mjs) 2385~2390행.
- 현재 검사는 요청자가 **파일 소유자의 프로젝트 중 하나에 참여하는지**만 확인합니다. 해당 파일이 속한 프로젝트에 참여하는지는 검사하지 않습니다.
- 재현: A 프로젝트에만 참여하는 작가에게 동일 소유자의 B 프로젝트 영상 URL을 요청하게 한 실제 핸들러의 메모리 DB 검사에서 `memberOfPrivateProject: false`, `authorized: true`가 확인됐습니다.
- 영향: 파일 URL을 알게 된 협업자가 자신에게 공유하지 않은 다른 프로젝트의 영상·음성을 받을 수 있습니다. URL을 추측하기 어렵다는 것은 권한 검사를 대신하지 못합니다.
- 수정 방향: 파일과 프로젝트의 관계를 관리하고 **파일별 소속 프로젝트 권한**을 검사합니다. 프로젝트 복제·라이브러리 재사용도 허용 범위를 명시해야 합니다.
- 완료 기준: 같은 소유자의 A에는 참여하고 B에는 참여하지 않는 계정으로 A 파일은 성공, B 파일은 거절되는 회귀 테스트.

### P1-02. AI 조수 되돌리기에서 협업 역할 제한 우회 및 다른 편집 덮어쓰기

- 위치: [assistant.mjs](../server/ai/assistant.mjs) 384~418행.
- 되돌리기는 대본 또는 장면 권한 중 하나만 있으면 통과합니다. 복원하려는 필드의 권한, 원 작업 실행자, 그 뒤 변경된 값은 확인하지 않습니다.
- 재현: 장면 권한이 없는 작가가 소유자의 이미지 작업을 되돌리는 실제 엔드포인트를 메모리 DB로 실행했을 때 성공 응답과 이미지 복원이 확인됐습니다.
- 영향: 작가가 이미지·영상 결과를 바꾸거나 편집자가 대사 변경을 되돌릴 수 있습니다. 이후 다른 팀원이 수정한 값도 과거 값으로 덮어쓸 수 있습니다.
- 수정 방향: 작업 종류·필드별 권한을 적용하고 소유자/실행자 정책을 정합니다. 현재 버전과 되돌릴 작업의 결과 버전을 비교해 충돌 시 안내합니다.
- 완료 기준: 역할별 허용/거절, 타인의 후속 수정 보존, 대기·실행·완료 작업별 되돌리기 테스트.

### P1-03. 공급사별 월 원가 한도를 신규 작업이 초과할 수 있음

- 위치: [engine.mjs](../server/ai/engine.mjs) 145~158행, 305~330행.
- 공급사 한도는 현재 누적 원가가 이미 한도 이상인지만 검사합니다. 새 작업의 예상 원가를 더한 검사는 플랫폼 전체 예산에만 적용됩니다.
- 재현: 실제 엔진의 메모리 대역 DB에서 공급사 한도 100원, 누적 99원, 신규 예상 원가 1,400원 조건이 등록되어 합계 1,499원이 되는 것을 확인했습니다. 실제 공급사에 비용을 발생시킨 검사는 아닙니다.
- 영향: 최고관리자가 설정한 공급사별 비용 상한을 신뢰할 수 없습니다. 플랫폼 전체 예산 설정이 일부 제한할 수 있지만 공급사별 한도를 대신하지 못합니다.
- 수정 방향: 공급사별 사용액·예약액·신규 예상 원가 합계를 트랜잭션 안에서 확인합니다. 동시 요청과 자동 대체 공급사에도 같은 검사를 적용합니다.

### P1-04. 썸네일 A/B 기능이 작품 표지 변경 제한을 우회

- 위치: [routes-serial.mjs](../server/routes-serial.mjs) 122~149행, `server/thumbs.mjs`의 공개 후보 적용.
- 일반 표지 변경은 초안·반려 상태만 허용하지만, A/B 후보 등록과 대표 이미지 확정은 작품 상태나 새 이미지 승인 여부를 확인하지 않습니다.
- 재현: 분리 API 서버에서 공개 작품의 일반 포스터 변경은 **409**, 동일 작품의 A/B 후보 추가는 **201**, 대표 이미지 확정은 **200**으로 응답했습니다.
- 영향: 관리자가 검토한 표지와 실제 공개되는 표지가 달라집니다. 심사 중 수정 잠금도 일관되지 않습니다.
- 수정 방향: 공개작 표지 교체 정책을 명확히 하고 승인된 후보만 노출합니다. 심사 중에는 변경을 잠그고 변경·승인 이력을 기록합니다.

### P1-05. Docker 배포 이미지에서 기본 자산의 서버 검증 경로 누락

- 위치: [Dockerfile](../Dockerfile) 14~16행, [server/index.mjs](../server/index.mjs) 983~999행.
- Docker runtime은 `dist`와 서버를 복사합니다. 반면 서버는 기본 아바타·포스터 등 파일 존재 여부를 `public/`에서 검사합니다. 배포 파일은 `dist/`에 있으므로 경로가 일치하지 않습니다.
- 영향: Docker로 AWS 배포 후 기본 아바타를 유지한 프로필 저장, 기본 포스터 사용 및 작품 심사 등에서 “등록된 파일을 찾을 수 없습니다”가 발생할 수 있습니다. 전체 소스가 있는 로컬 개발 서버에서는 드러나지 않습니다.
- 확인 수준: Dockerfile과 실제 파일 해석 코드를 대조하여 확인. 실제 Docker/AWS 실행은 하지 않았습니다.
- 수정 방향: 운영 자산 경로를 `dist`로 통일하거나 필요한 `public` 자산도 runtime에 포함합니다. 컨테이너 안에서 프로필 저장·표지 검사까지 실행하는 smoke test가 필요합니다.

### P2-01. 존재하지 않는 썸네일 파일도 A/B 후보·대표 이미지로 저장됨

- 위치: [routes-serial.mjs](../server/routes-serial.mjs) 123~149행.
- `/images/...webp`는 문자열 형식만 검사합니다. `/uploads/`도 DB 소유권만 확인하고 실제 파일 존재 여부는 확인하지 않습니다.
- 재현: 분리 API 서버에서 `/images/nonexistent-audit.webp`를 후보로 등록한 뒤 대표 이미지로 확정할 수 있었습니다.
- 영향: 목록·상세·공유 카드에서 포스터가 깨질 수 있습니다.
- 수정 방향: 등록·노출·확정 시 공통 미디어 검사를 적용하고 손실 파일은 대체 이미지와 복구 안내를 제공합니다. P1-04의 심사 정책과는 별개의 파일 유효성 문제입니다.

### P2-02. 대사 다시 쓰기 후 예전 립싱크 영상이 남음

- 위치: [routes-studio-ai.mjs](../server/ai/routes-studio-ai.mjs) 376~389행, [compose.mjs](../server/ai/compose.mjs) 114~119행.
- `rewrite_shot`은 대사가 바뀌면 음성은 지우지만 `lipsync`는 남깁니다. 합성은 립싱크 영상을 우선하고 별도 음성을 얹지 않습니다.
- 재현: 실제 결과 핸들러 실행 후 `dialogue: 새 대사`, `audio: 빈 값`, `lipsync: 이전 영상` 상태가 유지되는 것을 확인했습니다.
- 영향: 새 자막에 옛 대사가 재생되거나 변경 내용이 영상에 반영되지 않습니다.
- 수정 방향: 대사·화자 변경에 영향을 받는 음성·립싱크·합성 결과를 함께 무효화하고 재생성할 단계만 안내합니다.

### P2-03. AI 조수 화면의 실행 금액과 실제 예약 금액이 달라질 수 있음

- 위치: [Assistant.tsx](../src/studio/Assistant.tsx) 38~48행 및 135행, [assistant.mjs](../server/ai/assistant.mjs) 314~320행 및 353~356행.
- 버튼과 프로젝트 예산 확인은 계획 생성 당시 금액을 사용하지만, 실제 실행은 현재 선택한 모델을 사용합니다. 개별 작업에는 `budgetOk: true`가 전달됩니다.
- 조건: 계획 생성 → 모델을 더 비싼 것으로 변경 → 기존 계획 실행. 가격 변경도 같은 문제가 될 수 있습니다.
- 영향: PD가 확인한 라마보다 많이 예약되고 프로젝트 예산 초과 재확인이 생략될 수 있습니다. 실제 유료 모델 호출은 하지 않았으며 코드 경로로 확인했습니다.
- 수정 방향: 실행 직전 현재 모델·가격으로 전체 견적을 다시 계산하고 변경 금액 확인 후 실행합니다.

### P2-04. 일괄 업로드 중 수정한 제목·회차 번호가 실제 등록과 다름

- 위치: [EpisodeManager.tsx](../src/EpisodeManager.tsx) 222행, 252~256행, 902~912행.
- 업로드 시작 시 대기열 배열을 캡처합니다. 그러나 아직 업로드되지 않은 행은 처리 중에도 편집 가능합니다.
- 조건: 영상 두 개를 대기열에 넣기 → 첫 영상 전송 중 두 번째 제목·번호 수정 → 두 번째 등록. 화면에는 수정값이 보이지만 서버에는 시작 시 값이 전송됩니다.
- 영향: 잘못된 회차 제목·번호로 등록하거나 의도하지 않은 초안 회차를 덮어쓸 수 있습니다.
- 확인 수준: React 상태 갱신과 업로드 루프의 캡처값 사용을 코드로 대조. 네트워크 지연을 넣은 브라우저 재현은 수행하지 않았습니다.
- 수정 방향: 처리 중 메타데이터를 잠그거나 처리 직전 최신 대기열 값을 읽고 중복 번호·수정 가능 상태를 재검사합니다.

### P2-05. 네이티브 앱 공유 링크가 앱 내부 주소로 생성됨

- 위치: [App.tsx](../src/App.tsx) 2393행, [Channels.tsx](../src/Channels.tsx) 274행, `src/platform.ts`.

- 영향: Android/iOS 앱에서 공유할 때 `https://localhost` 등 외부 수신자가 열 수 없는 주소가 전달될 수 있습니다. 로컬 웹 링크 역시 외부 공유를 검증할 수 있는 주소가 아닙니다.
- 확인 수준: 코드 확인. 설치 앱·카카오톡 실기기 검증은 하지 않았습니다.
- 수정 방향: 공개 HTTPS 서비스 주소를 공유 전용 공통 설정으로 사용하고 실기기에서 카드·앱/웹 이동을 검증합니다.

### P2-06. 신작 정렬과 탭의 전체보기 조건이 맞지 않음

- 위치: [App.tsx](../src/App.tsx) 529~538행, 897~900행 및 발견 화면 1053행.
- 신작 탭은 공개일이 아닌 `NEW` 배지만 우선 정렬합니다. 최신순 계산은 별도로 존재하지만 이 탭에는 적용되지 않습니다.
- 신작·완결의 전체보기는 해당 필터를 전달하지 않고 기본 발견 페이지로 이동합니다.
- 영향: 최근 작품 탐색과 완결작 정주행 흐름이 끊깁니다.
- 수정 방향: 공개일·완결 상태 기준을 일관되게 적용하고 필터·정렬을 URL과 함께 유지합니다.

### P2-07. 중첩 확인창 Escape가 상위 편집창까지 닫을 수 있음

- 위치: [App.tsx](../src/App.tsx) 1964~1995행, [confirm.tsx](../src/confirm.tsx) 27~38행, [EpisodeManager.tsx](../src/EpisodeManager.tsx) 365~395행.
- 각각의 Modal이 `document`에 Escape 핸들러를 붙입니다. `stopPropagation()`은 같은 document에 등록된 다른 리스너를 막지 않습니다.
- 조건: 회차 관리 안에서 “예약 지우고 바로 공개” 같은 확인창을 연 뒤 Escape. 상위창의 닫기 조건도 충족하면 두 창이 함께 닫힐 수 있습니다.
- 영향: 저장 전 입력·대기열 상태를 잃을 수 있습니다. 코드로 확인했으며 해당 중첩 UI 조건의 직접 재현은 하지 않았습니다.
- 수정 방향: 최상단 모달만 Escape·초점·스크롤 잠금을 담당하는 공통 모달 스택을 사용합니다.

### P2-08. 실행 중 작업에 사용할 수 없는 ‘멈추기’를 표시

- 위치: [JobCenter.tsx](../src/studio/JobCenter.tsx) 202~206행, [engine.mjs](../server/ai/engine.mjs) 687~694행. AI 조수의 되돌리기 안내도 `Assistant.tsx` 58행 참고.
- PD 작업 센터는 대기·실행 상태 모두에 멈추기를 표시하지만 일반 취소 API는 실행 중 작업을 거절합니다. 관리자 강제 취소는 별도의 동작입니다.
- 영향: 비용을 막으려고 누른 PD가 이미 실행 중이라 취소할 수 없다는 오류만 받습니다. 조수 안내의 “진행 중 작업을 멈추고 반환” 표현도 실제 제한과 다릅니다.
- 수정 방향: 대기 중에는 취소, 실행 중에는 취소 가능 여부와 완료 후 조치를 명확히 표시하고 실제 반환 조건을 같은 문구로 안내합니다.

## 4. 업로드·심사에 대한 별도 판단

**기본 등록과 심사 흐름은 통합 테스트로 통과했습니다.** 업로드 자체가 전반적으로 안 되는 상태는 아닙니다. 다만 일괄 업로드 편집 시점 문제(P2-04)와 썸네일 경로(P1-04, P2-01)는 기본 흐름 밖에 남은 결함입니다.

- 기존 요청한 **관리자 별도 검토 팝업**은 구현되어 있습니다. 실제 브라우저에서 `#/studio/contents`를 유지한 채 표지·작품 소개·권리 정보·회차 영상·회차 선택 목록이 나타나는 것을 확인했습니다. 개발용 샘플 영상도 정상 로드됐습니다.
- 최초 작품 심사는 표지 로드·회차별 재생 준비·검토 확인·등록 오류 조건을 승인 버튼에 적용합니다(`src/ContentReview.tsx:392`).
- **공개 후 추가 회차 심사**는 승인 버튼이 `busy`만 검사합니다(`src/serial/EpisodeReviewQueue.tsx:238`). 영상 재생 실패 안내와 검토 완료 확인을 최초 작품 심사와 통일해야 합니다. 이를 서버 권한 우회로 분류한 것은 아닙니다.
- 관리자 메뉴의 심사 배지는 작품 대기만 계산합니다(`src/Studio.tsx:347`). 작품 심사와 추가 회차 심사를 함께 표시하면 새 회차를 놓치지 않습니다.
- **신작 첫 공개 예약**은 현재 기능 범위 밖입니다. 초안 작품에 추가한 회차도 `approved`로 저장되어 예약 API가 “이미 공개된 회차”로 409를 반환하는 것을 재현했습니다(`server/index.mjs:1234`, `server/routes-serial.mjs:53`). UI도 공개 작품의 연재 회차에만 예약을 노출하므로, 이를 기존 연재 예약 기능의 고장으로 보지는 않습니다. 첫 작품 예약 공개를 추가하고 초안 회차 상태·오류 문구를 정리할 필요가 있습니다.

## 5. 계정별 UI/UX 평가와 보완안

### 시청자

좋은 점: PC 중앙 콘텐츠·우측 메뉴, 모바일 하단 메뉴, 로고와 고정 헤더, 제목이 있는 썸네일, 랜덤 아바타, 보유 핑·구독·구매·시청 내역이 한 흐름으로 연결됩니다. 확인한 홈 이미지의 로딩 실패는 없었고 1280px/390px 화면에서 페이지 자체의 가로 넘침도 없었습니다.

우선 보완:

1. 비밀번호 분실 시 이메일 재설정, 이메일 인증·변경, 회원 본인 탈퇴 기능. 현재 비밀번호 변경·세션 종료와는 별개입니다.
2. 방송국 구독·문의 때문에 로그인한 경우 원래 화면으로 돌아오는 경로를 통일합니다. 작품 구매·찜에서 사용하는 복귀 처리를 공통 적용합니다.
3. 신작·완결 필터를 유지하고 공유 링크의 공개 주소를 통일합니다.
4. 실제 업로드 작품에도 항상 표시되는 “오리지널 콘셉트 데모 작품/시연 영상” 문구는 콘텐츠 출처와 운영 모드에 따라 분기합니다(`src/App.tsx:2385`).

### PD·초보 업로더

좋은 점: 로그인 즉시 전용 관리 화면, 내 작품·회차/방송국/정산/계정 메뉴, 4단계 제작 공간과 빠른 제작, 비용·실패·영상 업로드 안내, 검색 가능한 제작 가이드가 있습니다. 브라우저에서 PD 자동 이동과 모바일 메뉴·가이드 접근을 확인했습니다.

우선 보완:

1. 일반 가입은 시청자로만 생성됩니다. **PD 신청 → 관리자 승인 → 첫 작품 안내**를 제공해야 새로운 PD가 테스트 계정이나 관리자 수동 변경에 의존하지 않습니다.
2. 작업 공간에서 “다음 할 일”을 한 가지 기본 행동으로 강조하고 모델·고급 설정은 필요할 때 펼칩니다. 비용 견적과 실제 예약 금액을 같은 데이터로 표시합니다.
3. 새 협업 기능에 맞춰 역할별 할 수 있는 일, 누가 라마를 부담하는지, 승인 순서, 팀 탈퇴 후 접근 범위를 화면과 매뉴얼에 추가합니다. 현재 가이드는 기본 9개 목차 중심입니다.
4. 계정·방송국·작품·메인 편집에서 미저장 내용 보호를 통일합니다. `beforeunload`만으로는 앱 내부 메뉴 이동을 막을 수 없습니다(`src/HomeAppearance.tsx:159`). 임시저장 또는 이동 전 확인이 필요합니다.
5. 작업의 대기·실행·취소 가능·실패·반환·재시도 상태를 동일한 용어로 표현합니다. 결과가 바뀌면 다시 필요한 생성·합성 단계도 표시합니다.

### 최고관리자

좋은 점: 콘텐츠 심사, 회원·문의, 방송국·메인, 정산·출금·세무, 핑·라마, AI 공급사/API 키·모델·가격·능력표·라우팅·정책·작업 모니터가 분리되어 있습니다. 실제 AI 연결 준비 화면에서 “키는 나중에 등록”과 “실제 품질 검증은 별도” 안내도 확인했습니다.

우선 보완:

1. 작품·회차·표지 심사를 같은 검토 기준과 이력으로 관리하고, 재생 오류·반려 사유·재제출 변경점을 한눈에 보여 줍니다.
2. 공급사 예산 강제 제한을 수정한 뒤 사용액/예약액/예상액을 분리해 보여 주고 임계치 알림을 제공합니다.
3. 협업 역할 변경·되돌리기·표지 교체 같은 중요한 변경의 행위자·전후 값·시각을 감사 기록에 남깁니다.
4. 메뉴 수가 많으므로 운영 검색, 자주 쓰는 메뉴, 처리할 일 중심 대시보드를 제공합니다. 대규모 회원·작품·주문 조회에는 서버 페이지네이션과 검색을 적용합니다.

### 접근성·성능

- 모바일 관리 메뉴가 닫혀 있어도 `aria-expanded=true`로 나타나는 것을 브라우저에서 확인했습니다. 실제 표시 상태와 접근성 속성을 일치시켜야 합니다(`src/Studio.tsx:370`). 메뉴 열 때 초점 이동·닫을 때 복귀도 보완 대상입니다.
- 공통 Modal의 초점 대상에는 비활성·숨김 요소가 포함되고 링크가 제외됩니다(`src/App.tsx:1968`). 중첩 모달 수정과 함께 키보드 탐색을 검증해야 합니다.
- 모바일 화면의 작은 보조 문구·낮은 대비·아이콘만 있는 동작을 더 읽기 쉽게 조정할 여지가 있습니다. 정확한 색 대비 수치나 접근성 표준 전체 준수는 이번에 측정하지 않았습니다.
- 스튜디오 번들 크기 경고가 있습니다. 관리자·PD의 무거운 메뉴를 더 나누고 저속 네트워크·중저가 휴대폰에서 첫 진입 시간을 측정하는 것이 좋습니다. 현재 빌드 크기만으로 실제 속도가 느리다고 단정하지 않습니다.

## 6. 출시 전 별도 연동·검증 항목

아래는 이미 알려진 개발 단계의 제한이며, 미구현 기능을 구현 완료로 판단하지 않았습니다.

- 실제 결제·환불·구독 자동 갱신·스토어 인앱결제. 현재 테스트 결제는 운영 모드에서 차단됩니다.
- 카카오·네이버·구글 OAuth, 이메일 인증·복구. 화면은 연동 예정임을 안내합니다.
- 실제 AI API 키 등록 후 중국 모델을 포함한 공급사별 입력 형식·출력 품질·실제 원가·타임아웃·재시도 검증. 이번 검사는 모의 AI와 로컬 미디어 처리 기반입니다.
- AWS 컨테이너, RDS PostgreSQL에서의 전체 테스트와 동시성 검사. 이번 전체 테스트는 SQLite 분리 DB로 실행했습니다.
- 파일 영속 저장소·백업·복구. 여러 서버로 확장하려면 S3 등 공유 저장소와 공유 요청 제한이 필요합니다. 현재 로컬 MP4 구조를 대규모 스트리밍 완료 상태로 볼 수 없습니다.
- Android/iOS 설치 빌드, 실제 기기 영상·토큰·공유·뒤로가기·스토어 심사 검증.
- 실제 카카오톡의 공유 카드 캐시와 공개 URL 검사. 로컬에서 Open Graph HTML을 검사한 것과 실서비스 메시지 카드 검증은 다릅니다.
- 약관·개인정보 문서의 운영용 정비. 이번에는 법률 적합성을 심사하지 않았습니다.
- 배포·사용 설명 문서의 현재 기능 반영. 과거 검수 보고서의 이미 고친 결함을 그대로 현재 결함으로 재인용하지 않았습니다.
